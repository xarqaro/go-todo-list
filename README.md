# Дипломный проект: планировщик задач на Go

Проект рассчитан на два спринта. Уроки главы "Дипломная работа" (спринты 13-14) идут по шагам и
дают подсказки и примеры кода, этот файл собирает требования в одном месте.

Сообщение от тимлида:

> Фронтенд планировщика готов: страница со списком задач, диалог добавления и редактирования,
> поиск, страница входа. Бэкенда нет совсем. Его пишешь ты, с нуля: веб-сервер, база SQLite, API
> и правила повторения задач.
>
> Контракт API зафиксирован фронтендом и тестами в `tests`. Зелёные тесты это минимум, с
> которого я начну смотреть проект: планировщик в браузере тоже должен работать без ошибок.
>
> Код разложи так, чтобы в нём можно было найти, где сервер, где API, а где база. Всё в одном
> файле я верну на доработку, даже если всё работает.

## Что в репозитории

- `web/`: готовый фронтенд (`index.html`, `login.html`, `css/`, `js/`), ходит в `/api/...` на том же адресе
- `tests/`: HTTP-тесты по шагам, от `TestApp` и `TestDB` до `TestDone` и `TestDelTask`; ходят в
  запущенный сервер и читают базу напрямую
- `tests/settings.go`: `Port = 7540`, `DBFile = "../scheduler.db"`, флаги `FullNextDate`, `Search` и `Token`
- `go.mod`, `main.go` и серверного кода нет: модуль создаёшь ты

## Что сделать

Форматы запросов, ответов и правил повторения смотри в уроках главы "Дипломная работа".

1. Веб-сервер на порту 7540 отдаёт файлы из `web/`; файл-сервер и API вешай на один маршрутизатор, иначе `/api/...` даст 404.
2. При старте создай в корне `scheduler.db` с таблицей `scheduler` и индексом по `date`, если файла нет.
   Пустой файл, оставленный тестами, удали: проверка "есть ли файл" его пропустит, таблицы не будет.
3. `GET /api/nextdate` с правилами `d <число>` и `y`.
4. `POST /api/task`: добавление с проверкой данных.
5. `GET /api/tasks`: список по дате; нет задач, значит `{"tasks": []}`, а не `null`.
6. `GET /api/task` и `PUT /api/task`; `id` в ответе GET нужен, хоть в уроке его нет.
7. `POST /api/task/done` и `DELETE /api/task`.
8. Замени этот файл своим `README.md`: что делает проект, какие звёздочки сделаны, как запустить и какой адрес открыть, как гонять тесты и с какими `settings.go`, Docker, если есть.

По желанию: `TODO_PORT` и `TODO_DBFILE`, правила `w` и `m`, поиск `?search=`, вход по `TODO_PASSWORD` с JWT, `Dockerfile`.

## Готово, когда

- сервер запускается из корня (`go run .`) и при первом старте создаёт `scheduler.db`
- при запущенном сервере `go test ./tests` проходит с настройками по умолчанию
- для каждой сделанной звёздочки тесты проходят с флагом: `FullNextDate`, `Search`, токен из `/api/signin` в `Token`
- на `http://localhost:7540/` задача добавляется, редактируется, выполняется и удаляется без ошибок
- код разложен по смыслу: сервер, обработчики API, работа с базой
- в корне твой `README.md` с пунктами из шага 8

## Не засчитаем

- правку тестов, кроме значений в `tests/settings.go`: подогнанный тест прячет сломанное в браузере
- весь сервер в одном файле: вернём на доработку даже при зелёных тестах

## Как начать

Форк уже создан платформой в твоей группе GitLab, "Форк" нажимать не нужно.

```bash
git clone <ссылка на твой форк>
cd go-final-project
git switch -c first-iteration
go mod init <имя модуля> && go mod tidy
go test ./tests        # сейчас падает: сервера нет, TestDB паникует и оставляет пустой scheduler.db
```

Когда тесты зелёные, открой Merge Request из своей ветки в `main` своего форка: ментор и AI-ментор увидят его сами, ссылку отправлять не нужно.
Сервер держи в одном терминале, тесты гоняй из корня во втором, например `go test -run ^TestApp$ ./tests`.
`TestTasks` очищает таблицу `scheduler`, не держи там ничего ценного.
